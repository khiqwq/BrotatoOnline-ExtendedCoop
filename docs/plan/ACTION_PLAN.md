**ACTION PLAN：兼容 Brotato Online 的 5～8 人合作 Mod**

日期：2026-10-28。状态：待执行。关联背景文档：BACKGROUND.md。

本文件定义接下来执行的工作、顺序、产物和通过条件。所有任务初始为 TODO；本轮只编写执行计划，未创建开发仓库、实现 Mod、配置 CI 或完成游戏测试。背景文档提供技术依据，本文件作为执行清单；范围变化需同步更新两份文档并记录原因。

**1. 执行目标与里程碑**

交付目标：一个独立扩展，配合未经手动修改的客户指定工坊版 Brotato Online，支持每机一名玩家、最多 8 人完整合作流程；1～4 人保持基线体验；超四人界面沿用原版视觉资源；异常处理覆盖背景计划的 18 类风险。

默认技术路线使用匹配游戏版本的 Godot 3.x / GodotSteam、GDScript 和现有 Mod Loader。技术选型、加载方式和精确版本由 AP-002/AP-005 验证后固定。暂不引入新的后端服务、数据库或网络协议栈。

| 里程碑            | 必须提交的成果                                             | 放行条件                                        |
| ----------------- | ---------------------------------------------------------- | ----------------------------------------------- |
| M0：环境与基线    | 范围表、版本锁、四人基线、限制清单                         | AP-001～004 完成，能重复运行同一基线            |
| M1：独立补丁可行  | 扩展加载证据、五人短流程、八人槽位/LAN 演示                | AP-005～007 完成；原工坊 Mod 指纹未变化         |

**2. 轻量项目规范：在第一批任务中建立**

采用一个仓库、一个主开发分支和短期功能分支。开发者可兼任测试负责人；角色用于明确责任，不要求扩充团队。

| 角色             | 责任                                                         |
| ---------------- | ------------------------------------------------------------ |
| 实现负责人 DEV   | 代码、适配、打包、技术调查和修复；每项任务只有一名直接负责人 |
| 验证负责人 QA    | 复现、场景执行、日志/录像核对和回归；单人时与编码分开检查并记录 |
| 需求负责人 OWNER | 锁定支持范围、确认界面样例、接受范围变更及验收；可由接单方对接客户 |

工作项使用固定编号 AP-001～024。实现缺陷使用 BUG-xxx，并关联任务、风险 Fxx 和测试 Txx。每个工作项在 Issues 或仓库内同一份任务表维护，选择一个作为状态来源，不并行维护互相矛盾的看板。

工作流：TODO → READY → IN_PROGRESS → REVIEW → VERIFY → DONE；受阻时标为 BLOCKED，保留阻塞条件、已尝试方法和可继续事项。没有日志/测试证据的工作不能标为 DONE。

单名开发者同时推进一项主要实现任务；小型独立文档/测试准备可以穿插。实现任务尽量拆为 0.5～2 个工作日可验收的改动；超过 2 天且未得到可运行结果时，按调查、适配、验证继续拆分。M0～M1 暂按背景计划的 4～7 个工作日调研预算安排，之后依据证据重新估算，不把该预算当成功保证。

开始前定义 DoR（可开工条件）：依赖已满足；目标版本明确；问题或预期行为可描述；验收结果可观察；所需测试资源可用。探索任务的 DoR 可以是明确假设、时间盒和要回答的问题。

完成时执行 DoD（完成条件）：实现符合范围；相关自动检查通过；运行目标环境验证；必要回归通过；证据关联到提交；文档/兼容表已更新；无泄漏的测试输入或信号；不存在未披露的行为变化。纯文档工作执行链接与内容核对，不强制运行游戏。

提交使用简短的类型前缀，如 feat、fix、test、docs、build；关联工作项。PR/变更记录只要求问题、最终行为、验证证据、存档/协议影响和回滚方式。采用 SemVer 管理扩展版本；网络能力版本与存档 schema 独立演进。增加不兼容行为时明确升级规则，不仅修改展示版本号。

**3. 目标仓库结构与开发入口**

以下是 AP-002 要创建的目标结构，当前尚未存在。Namespace/ModName 在 AP-001 固定，示例占位符不得进入正式安装包。

```text
repository/
  README.md
  CHANGELOG.md
  LICENSE
  THIRD_PARTY_NOTICES.md
  .editorconfig
  .gitattributes
  .gitignore
  project.lock.json
  mods-unpacked/<Namespace>-<ModName>/
    manifest.json
    mod_main.gd
    compatibility.json
    scripts/
      compatibility/       # 上游接入和版本适配
      core/                # 容量、身份与槽位等规则
      network/             # 扩展协商、提交与阶段控制
      persistence/         # 超四人检查点与恢复
      diagnostics/         # 运行检查与脱敏报告
    extensions/            # 实际扩展的原版/上游脚本
    ui/                    # UI 适配和自有资源
    translations/
  tests/
    unit/                  # 无完整商业游戏文件也能运行的规则测试
    integration/           # 目标游戏/上游 Mod 的契约与加载验证
    scenarios/             # Txx 实机用例、故障事件、预期结果
    fixtures/              # 自建的脱敏最小数据
  tools/
    setup.ps1
    check.ps1
    test.ps1
    package.ps1
    verify-package.ps1
  docs/
    requirements.md
    compatibility.md
    limits-audit.md
    adr/
    runbooks/
  evidence/                # 版本化证据索引；大录像/原始日志放本机或受控位置
```

不要为每个概念强建类；先形成可独立验证的模块，再根据实际复杂度拆分。游戏界面使用 Godot 原生场景/控件，不引入 Web 前端框架。Godot 3 的语法/API、测试运行器和格式化工具必须匹配目标版本。

project.lock.json 锁定编辑器/GodotSteam 构建、工具版本、上游提交和目标工坊文件的规范化指纹、构建参数。compatibility.json 从已审核的支持记录生成，只包含运行时需要的适配信息；CI 检查两者一致，避免手工维护两份冲突的支持表。

恢复出的游戏项目、商业资源、测试存档、Steam 凭据、重连令牌、缓存和临时下载不进入仓库或安装包。完整游戏集成环境在本机忽略目录中准备。任何引用的参考 Mod 代码在进入仓库前记录来源与许可。

AP-002 先实现最少的 setup/check/test 入口；package/verify 随 AP-022 完成。计划中的调用形式如下，不能把它们当作当前已经可运行的命令：

```powershell
pwsh ./tools/setup.ps1 -GamePath <本机游戏路径>
pwsh ./tools/check.ps1
pwsh ./tools/test.ps1 -Suite Unit
pwsh ./tools/test.ps1 -Suite Integration -GamePath <本机游戏路径>
pwsh ./tools/package.ps1 -Version <候选版本>
pwsh ./tools/verify-package.ps1 -PackagePath <安装包路径>
```

setup 仅验证本机安装与生成本机配置；安装或复制到游戏目录必须有明确目标并备份受影响文件，不自动替换上游 Mod。所有入口遇错返回非零退出码；未具备条件的集成测试标记 SKIPPED 并写原因，不能算 PASS。

**5. M1 操作手册：第一批必须跑出的结果**

1. 建立测试专用用户数据目录/隔离配置，验证自动保存不会落入日常存档；保存游戏和上游 Mod 的规范化指纹。
2. 装载最小独立扩展，打印实际实例使用的脚本、继承关系和关键生命周期计数，确认上游文件没有被修改。
3. 从 4 人增加到 5 人，记录每台机器的成员、稳定槽位、当前索引、虚拟动作及 RunData 人数。检查设备唯一性和本机归属。
4. 给各角色分配不同且可识别的装备/操作，进入战斗并分别移动/攻击；通过一次升级/箱子、一次商店购买，再进入下一波。
5. 在上述提交边界对照 Host 和客户端的 roster、人数、装备、经济结果；确保场景保护没有裁掉第五人。
6. 加到 8 个逻辑槽位，逐通道输入；运行 8 个独立 LAN 实例，完成开局及一次菜单切换，记录槽位池使用情况。
7. 回到 1～4 人验证开局和退出；再次比较上游文件指纹，输出 M1 报告。

M1 报告必须回答：独立补丁是否成立、哪些内部方法被覆盖、初始化是否可靠、八人输入是否足够、仍未验证哪些功能。每次失败保留最小复现。AP-005/AP-006 在约定时间盒内无法取得新证据时，收敛为阻塞报告，列出所需上游接口；不无限重试或悄悄转为定制联机分支。

故障注入分别在传输与应用边界实现：可靠通道的丢包主要验证底层重传和超时，重复/乱序命令通过应用事件注入验证去重。不要假装在可靠通道上直接丢一条业务命令就等同真实网络丢包。调试故障参数不向普通玩家暴露，并从正式包剔除。

协议故障测试还需要覆盖伪造他人槽位、超范围索引、过大列表/载荷、重复会话、旧 run/phase/roster 代次；无效输入应拒绝并记录脱敏原因，不能触发崩溃或无限分配。

证据记录统一包含：任务/需求/风险/测试编号、提交与安装包 SHA-256、锁定环境、人数、后端、输入/DLC/Mod 组合、随机种子/事件序列、预期/实际、结果 PASS/FAIL/SKIPPED、日志/录像索引、关联 BUG。关键运行状态比较限定在已提交边界；日志不输出凭据或重连令牌。

**7. CI、测试与打包规范**

采用分层检查，避免把缺少商业游戏文件的公共 CI 当作完整游戏验证。

| 检查层             | 自动化内容                                                   | 运行环境及门槛                                               |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 每次变更           | Godot 3 兼容的格式/语法检查、manifest/schema、版本锁一致性、包路径白名单、纯规则测试 | 普通 CI；必须通过。语法通过不等于游戏 API 可用               |
| 涉及核心逻辑的变更 | 参数化槽位/身份/容量规则、动作幂等、阶段代次、存档读写/中断夹具、可重放事件测试 | 最小 Godot 3 测试项目；断言行为，不为每个常量编写镜像测试    |
| 涉及上游适配的变更 | 实际目标 GodotSteam、游戏资源/脚本、Mod Loader 加载与扩展顺序、1/4/5/8 人短流程 | 具备合法游戏安装的本地/受控执行环境；记录运行证据，不上传游戏文件 |
| 发布候选           | 背景计划完整矩阵、真实 Steam 多账号、LAN、故障、视觉、长测、性能和保存恢复 | RC 专项验收；不能被单机模拟替代                              |

只在已有测试体系不足时选择一个与目标 Godot 3 版本兼容的测试工具，固定版本；优先使用项目最小运行器，不预设引入多个测试框架。纯规则模块尽量避免依赖完整 SceneTree/Steam，集成测试负责证明适配器与真实游戏协作正确。

有向网络状态、身份、数据持久化改动必须有失败路径测试。UI 低风险资源/样式修改采用目标画面的视觉检查，行为改动增加交互回归。每个新缺陷先确定最小复现，修复后补能防止重现的测试或实机用例。

打包采用白名单，只包含 manifest、入口、自有扩展/脚本、必要 UI/翻译和许可证。脚本固定文件顺序、路径规则、时间戳与编码，校验两个相同输入构建的 SHA-256；同时输出源提交、工具/上游版本、文件清单和第三方来源。包内不含测试开关、参考游戏工程、Steam 数据或个人配置。

版本标签和安装包对应同一个已验收提交，禁止在打包时隐式拉取上游 latest。生成包后校验路径穿越、遗漏文件、重复 Mod 标识、依赖与版本声明，再在干净环境安装。安装包有实质变化就产生新的 RC 编号/校验和，并重跑受影响的验收；不能沿用旧包测试记录。

**8. 技术决策与范围控制**

只为影响交付或难以回退的选择写简短 ADR，内容包括背景、选择、依据、代价和验证：

- ADR-001：独立补丁加载与覆盖方式；AP-005 产出，M1 更新结论。
- ADR-002：虚拟输入、稳定身份和索引映射；AP-010 产出。
- ADR-003：菜单提交、阶段与上游混合同步边界；AP-011/AP-012 产出。
- ADR-004：超四人存档、schema 和检查点提交；AP-016 产出。

对 8→16 人、增加每机多角色、主机迁移、旧参考 Mod 存档迁移、新增 DLC/Mod 支持等变更，先记录新增行为、受影响任务/测试和资源成本，再调整承诺。普通实现细节由 DEV 决定，不为可逆的局部选择增加审批流程。

严重度分级：S0 为进度损坏、身份/装备串位、重复经济提交等数据正确性问题；S1 为核心流程无法完成、崩溃、持续卡死；S2 为有明确绕行的次要功能问题；S3 为视觉或文案细节。S0/S1 阻断 M4/M5。任何等级只要违反已确认的核心验收要求，也不能直接放行；允许延期的问题必须有影响说明、绕行方案和接受记录。
