**PLAN：兼容 Brotato Online 的超四人合作 Mod**

编写日期：2026-10-28。状态：开发计划与源码可行性评估，尚未完成游戏内验证。

**1. 目标与可行性判断**

制作一个最多支持 8 人的《土豆兄弟》合作 Mod，优先以独立扩展形式，与客户指定的 [Brotato Online，Workshop ID 3741034628](https://steamcommunity.com/sharedfiles/filedetails/?id=3741034628) 同时启用。每位玩家在自己的电脑上运行游戏，每台电脑控制一个角色，通过 Brotato Online 联机。

8 人是本计划的默认交付上限，属于规划假设；如果客户要求 16 人或更高，需要重新评估输入映射、界面密度、网络流量与性能，不能直接沿用本估算。

技术上具备实现基础：已有联机源码，也有超四人本地合作项目可以参考。当前不能保证“未经修改的工坊版 Brotato Online + 独立扩展”一定可行。首个里程碑必须证明第三方脚本扩展可以在正确的加载时机接管人数、槽位和场景保护逻辑。

可行性分成两层：

| 目标                                             | 当前判断                   | 必须取得的证据                                               |
| ------------------------------------------------ | -------------------------- | ------------------------------------------------------------ |
| 实现 5～8 人合作，并沿用 Brotato Online 网络能力 | 有条件可行                 | 实机验证玩家数据、输入、流程与同步均能扩展                   |
| 保持原工坊 Mod 文件不变，仅安装独立补丁完成兼容  | 待验证，是优先路线         | 在目标 Mod Loader 上证明扩展注册时机、方法覆盖和初始化顺序有效 |
| 仅调用公开 API 自动解除所有人数限制              | 当前源码不足以支持这个判断 | 公开 API 没有直接提供人数容量设置接口                        |
| 对所有未来版本和任意第三方 Mod 永久兼容          | 不作为承诺                 | 使用版本适配、检测、明确拒绝和回归测试控制风险               |

本次只交付计划；不将源码分析或现有 Mod 的作者说明写成已经通过实测的结论。

**2. 需求边界与交付定义**

首版需要覆盖：

- 1～4 人维持目标基线版本的正常操作和界面表现；5、6、7、8 人均可完整游玩。
- Steam 好友邀请、公共大厅、LAN 联机；Steam 与 LAN 分别验证，不默认承诺两种连接方式混接在同一房间。
- 角色选择、武器选择、难度/区域选择、战斗、升级、箱子、商店、下一波、失败、胜利、结算、继续存档。
- 玩家死亡、复活、观战及目标版本已有合作机制在第 5～8 个槽位正常运作。
- 在原 Mod 支持的时机和方式下断线重连；保留其身份校验语义，不擅自开放战斗中换人或任意玩家中途加入。
- 超四人异常的检测、恢复、退出与诊断机制，详见第 8 节。
- 保持原版字体、图标、面板、按钮、角色和整体画风；超四人布局按确认后的截图验收。

首版不默认包含主机迁移、专用服务器、每机多人输入、16 人、手机/主机版、所有第三方 Mod，以及自动兼容未来游戏更新。房主退出时优先安全结束会话并保留最近有效检查点。

“兼容”必须在发布说明中写为：具体游戏版本 + Mod Loader 版本 + Brotato Online 文件指纹/版本 + 扩展版本 + 已验证 DLC/其他 Mod 组合。参考 Mod 不等于运行依赖。

**3. 技术基线与已核实的限制**

技术栈采用与目标游戏相匹配的 Godot 3.x / GodotSteam、GDScript、Godot Mod Loader，以及 Godot 原生 UI 场景。项目恢复和本地调试采用社区文档描述的 GDRE Tools 工作流；精确编辑器版本必须从目标安装包确认，不直接升级到 Godot 4。

本次下载并检查的 Brotato Online 参考提交：`53d3fd4528df3226043b1c188c3b12bc6957c515`。这是 GitHub 源码快照，不保证与客户订阅到的工坊文件完全一致。

该快照 manifest 声明游戏版本为 `1.1.15.4`、Mod Loader 为 `6.2.0`。README 中协议版本与实际脚本常量存在差异，因此开发时以实际运行文件和握手结果为准，不能只看 README 或 manifest 的展示版本。

禁止全局把数字 3/4 替换为 7/8。例如 ENet 的通道数量、通道编号范围与玩家数量不是同一概念，武器等级等游戏数值也不能误改。

**5. 实现路线与可行性闸门**

路线 A，优先：独立扩展与未经手动修改的目标工坊版 Brotato Online 同时运行。使用 Mod Loader 的脚本扩展/资源扩展能力，在合适时机覆盖容量相关方法、输入映射和人数保护路径；保持原联机层的会话、消息和身份能力。

Godot Mod Loader 的脚本扩展基于继承，父方法仍可能直接使用自己的常量。不能假设给对象设置一个同名属性或在子脚本声明一个数字就能改变全部逻辑。P1 必须验证确切可覆盖的方法、调用路径、加载先后及常量引用行为。

已知风险是部分 Manager 由 Mod 自己 `load()` 和 `set_script()` 创建。应验证扩展注册是否作用于这些脚本，且在首个实例运行前生效。不能在已运行 Manager 上随意替换脚本，导致丢失成员状态、重复信号连接或重复 `_ready()`。加载顺序以实际日志证明，不能只凭 manifest 依赖字段推断。

路线 B，条件选项：在原作者接受接口改动后，让目标 Brotato Online 提供容量查询、虚拟槽位分配和版本能力协商接口，再由独立扩展调用。计划可以准备必要改动说明，但不把联系作者、对方回复或合并当作已有条件。

路线 C，备选：维护修改过的 Brotato Online 分支。如果只有这条路线能完成，必须明确标为“定制联机版本”，不能宣称已满足“与原工坊版兼容”。切换交付路线需要客户认可该范围变化；本计划本身不包含对外联系或发布操作。

P1 的通过条件：

1. 在原工坊版文件未被手改的条件下，证明独立扩展生效；记录文件哈希、注册顺序、实际脚本继承链和关键运行日志。
2. 5 个真实客户端走通选人 → 战斗 → 升级/箱子 → 商店 → 下一波；每个角色的数据、输入、消费及准备状态均对应正确玩家。
3. 8 个逻辑槽位与输入映射完成压力验证，并用 8 个独立 LAN 实例验证最小开局与至少一次菜单切换；Steam 多账号验证在后续阶段完成。
4. 首次切场景后玩家数据没有被截成四人，保护脚本未覆盖扩展结果；1～4 人仍可正常开局。

如果独立补丁路径失败，交付失败点、复现和可选改动方案。不得用分支版本成功或 Parsec 演示代替路线 A 通过。

**6. 建议的内部模块与关键约束**

以下模块名称是拟议设计，尚未实现；实施时按目标版本调整边界。

| 模块                 | 责任                                                         |
| -------------------- | ------------------------------------------------------------ |
| CompatibilityAdapter | 检查游戏/Mod 文件版本与关键方法，集中封装对上游内部脚本的接入，避免各处散落路径依赖 |
| CapacityPolicy       | 管理最大容量、会话成员数、在局角色数、当前在线数的不同含义；在创建会话时确定容量，对局中不随意改变 |
| SlotRegistry         | 管理持久身份、逻辑槽位、当前 player_index、虚拟输入设备、本机归属的映射 |
| FlowGuard            | 管理阶段和场景代次，验证切换前后的人数与数据，抛弃旧场景消息，防止重复推进 |
| NetworkCompatibility | 扩展能力协商、版本验证、消息去重、状态请求/确认、连接超时处理 |
| CoopUIAdapter        | 从同一份槽位数据生成页面，复用原主题与控件，管理本机焦点和全员准备状态 |
| ExtendedRunStore     | 分离超四人对局存档、检查点、身份信息和迁移；处理恢复与回滚   |
| Diagnostics          | 记录异常类型、阶段、槽位摘要、恢复结果，生成可复现的问题报告 |

关键约束：

- 统一最大容量不意味着所有地方都使用同一个人数。断线时在线数减少，但在局角色数通常应保持；死亡人数也不能被误用为槽位数量。
- 每个持久角色槽位有稳定标识，玩家显示编号为 P1～P8；原生零起始 player_index 仅是当前映射，不能直接作为跨重连身份。
- 所有按玩家索引保存的数组/队列均按在局槽位数构造。变更 roster 时，统一重映射装备、商店、升级、身份、统计和网络缓存。
- 准备、购买等改变共享结果的新增操作由 Host 验证并提交；继续遵守上游原有混合同步方式，不强行把整个战斗重写为完全 Host 权威。
- 客户端提交操作时必须验证发送者是否拥有目标槽位，不接受通过伪造 player_index 操作他人角色。
- 在已提交的阶段边界验证 Host 与 Client 的槽位布局和核心状态；不要求每一帧的表现数据完全一致。
- 防止重复信号与生命周期回调；退出清理必须释放远程输入、解绑信号并清除本局缓存。

**7. 核心工作包**

**7.1 人数、输入与数据扩展**

- 审计 CoopService 最大人数、RunData 人数设置、玩家生成、颜色表、输入动作、队列、合作统计及缩放公式，建立限制清单。
- 将联机层容量判断、LAN 建服容量、菜单/主场景/玩家生成保护统一接入会话容量规则；保留非法值检查，合法的 5～8 人不再被静默截断。
- 为每个远程逻辑角色分配独立虚拟输入通道；优先兼容原 InputService，必要时注册扩展动作或增加适配层，并覆盖游戏、菜单、确认、取消、暂停与瞄准。
- 处理实体手柄的保留设备和键盘特殊设备号，保证 7 个远程角色不会占用本机真实输入。网络逻辑槽位与 Windows 实体 XInput 数量分离。
- 围绕 P5～P8 检查攻击、拾取、伤害来源、复活、共享效果、炮台/宠物等归属、统计与结算；不能只检查移动。
- 默认保留原版合作平衡规则，但检查超过四人时数组查表、上限、取整、掉落归属、敌人数等是否安全；任何平衡改动写入规则说明。

**7.2 菜单与同步**

- 给选人、武器、区域/难度、升级、箱子、商店和结算逐一标记本机操作范围、Host 决策和同步状态。
- 准备状态依据有效在局 roster 计算，防止只等待前四人、漏掉后四人或永远等待断线成员。
- 购买/出售/刷新/锁定/升级等动作带去重标识；重复包、重复点击和确认重发只产生一次最终结果。
- 场景切换携带当前 run、wave、phase 和 roster 代次；旧战斗/旧商店消息不能作用于新场景。
- 沿用上游传输与快照，审计玩家列表、包大小、分块、发送队列及超时预算；超四人全员都必须运行匹配的扩展版本。
- 大厅元数据展示实际容量与扩展能力；客户端加入后在进入正式流程前完成能力验证。不兼容者获得明确提示并安全退出。
- 扩展能力不能仅靠 Mod 列表或显示版本判断；协议协商消息不得与现有上游消息类型冲突。

**7.3 原版画风与扩展界面**

- 1～4 人保留基线界面，截图回归时以“相同游戏与 Brotato Online 版本，未启用人数扩展”的页面作对照。
- 5～8 人先制作使用原主题的真实界面样例。默认候选为两行、每行最多四个玩家面板；确认可读性后固定布局规则。
- 同时容纳所有玩家不必机械缩小所有文本：商店长描述可复用原 tooltip/详情区域，确保本机完整操作内容始终可读。
- 覆盖角色选择、武器选择、升级、箱子、商店、战斗 HUD、玩家列表、暂停、继续游戏的角色归属、结算及错误提示。
- P5～P8 使用与原版协调且可区分的颜色，并显示玩家编号/名字；颜色不是唯一识别方式。
- 手柄焦点只能落在本机可操作区域，布局重建后保持有效焦点；鼠标与手柄混用不触发他人面板。
- 以 1280×720、1920×1080、2560×1440 为默认验证分辨率，另测窗口缩放与 21:9。更低分辨率如无法保持信息密度，使用原风格分页/详情机制或明确支持下限，不静默裁切。

视觉验收应写成“资源和风格一致，扩展布局按截图确认”。人数翻倍后布局不可能同时保持原四人页面的全部位置与尺寸。

**8. 超四人 unexpected behavior 的兼容机制**

原则：可恢复的已知状态用明确机制恢复；涉及归属、经济、存档等无法可靠判断的状态，暂停相关推进并退回安全检查点/大厅。不得吞掉错误继续运行，也不得通过删除 P5～P8 来伪装恢复成功。

| 异常/触发场景                        | 检测                                 | 处理与回退                                                   | 必测结果                          |
| ------------------------------------ | ------------------------------------ | ------------------------------------------------------------ | --------------------------------- |
| 成员数、槽位数、players_data 不一致  | 创建会话、切场景和提交检查点时校验   | 初始化缺失的空槽位须使用完整初始化流程；有装备/身份的数据异常请求 Host 重同步，无法恢复则停止推进 | 不把有效 8 人裁成 4 人            |
| 输入设备池耗尽、设备号重复           | 分配前校验本机保留号与全局唯一性     | 分配新的受支持虚拟通道并注册动作；失败时拒绝该次加入并给出原因 | 不让两人控制同一角色              |
| 实体手柄拔插、切换输入设备           | 本机设备变化事件与归属检查           | 清除旧输入，保持逻辑角色身份，重新绑定本机设备               | 不新增幽灵玩家，不持续自动移动    |
| UI 少创建面板/颜色表越界             | 面板数量、槽位编号、资源索引检查     | 按槽位重建 UI，扩展颜色与焦点；必要时使用详情/分页           | P5～P8 可见且可操作               |
| 准备/升级/箱子队列漏槽、重复消费     | 每槽队列、动作标识、阶段检查         | Host 校验并返回结果；重复消息只重发结果，不重复执行          | 不重复扣款、加属性或给道具        |
| 多人同时确认导致重复开局             | 阶段代次与提交状态                   | Host 仅提交一次；迟到确认成为无操作                          | 只生成一组玩家和一个新波次        |
| 慢客户端尚未加载，快客户端已发送操作 | 场景就绪确认和代次检查               | 临时等待/请求最新状态，丢弃失效操作；超时给出重试/回大厅路径 | 不把旧场景节点当新场景使用        |
| 延迟、丢包、乱序和重复包             | 序号、去重标识、阶段/波次、确认超时  | 菜单操作可靠确认；表现状态采用最新有效快照；重试有次数/时间上限 | 不无限等待、不重做经济操作        |
| 玩家断线                             | 连接心跳、上游断线事件               | 按上游规则保留身份与槽位，释放按键；到达需本人选择的阶段时提示房主等待、恢复或安全处理 | 不直接压缩数组导致全员串位        |
| 原玩家重连/改变加入顺序              | Steam 身份或上游 LAN 身份机制        | 由 Host 校验并恢复原角色槽位、数据和阶段；必要时走主菜单继续流程 | 角色/装备跟随身份，不跟随加入次序 |
| 局中踢除掉线成员、roster 缩减        | roster_generation 与统一映射         | 在上游支持时机提交完整重映射；所有客户端确认后才继续，保存新检查点 | 商店、属性、统计和身份一起变更    |
| 房主退出、崩溃                       | 连接终止/超时                        | 客户端安全退回主菜单，释放输入；重新由原房主恢复最近有效检查点 | 无卡死，不承诺无损恢复未保存战斗  |
| 超四人存档被原版/缺扩展环境读取      | 存档格式、容量及扩展版本检查         | 使用独立对局存档，缺扩展时不把它交给原版继续流程             | 原版存档与超四人存档互不破坏      |
| 保存中断、损坏、迁移失败             | 完整性检查、schema、提交标识         | 写临时文件、校验后提交，保留上一有效副本；失败保留旧档，不覆盖原档 | 可恢复或给出清楚错误              |
| DLC 或内容资源不一致                 | 启动/加入时检查内容能力与资源可用性  | 沿用并验证上游 DLC 协商；无法保证资源一致时阻止开局，不能临时乱换道具 | 无缺资源崩溃与静默装备变化        |
| 其他 Mod 改写同一 UI/服务            | 已知冲突清单、脚本链与运行检查       | 确认兼容的组合才启用适配；未知组合提供诊断，已知危险组合禁止超四人开局 | 不把“没有报错”作为兼容通过        |
| 更新后方法/节点结构变化              | 版本、方法、签名/资源及指纹探测      | 进入受支持版本适配；未验证时关闭超四人新局并提示，已有超四人档保持隔离 | 不在不支持结构上强行运行          |
| 多人带来掉帧、发送队列积压           | 帧时间、流量、包大小、积压和处理耗时 | 优先减少无效广播、表现更新与重复查询；必要时拒绝高于实测容量的新局 | 不丢弃购买、升级等必要状态        |

恢复次数必须有限，同一问题多次恢复失败就停止阶段推进，提供明确下一步。对局中的不兼容不能静默降级为四人；回到主菜单后才允许建立新四人局。

所有恢复都记录：版本/指纹、会话与阶段代次、槽位数、归属摘要、异常原因、恢复动作和结果。日志中不保存重连令牌等秘密；导出的身份信息应脱敏。

**9. 存档与继续游戏专项**

超四人对局采用独立的运行中存档路径和 schema，不覆盖原版角色解锁/永久进度文件；原 Mod 可能会写入普通局内存档，必须审计并覆盖所有相关保存、自动保存、读取和继续入口，不能只更改一个保存路径。

保存内容包括：Run ID、schema、扩展与适配版本、容量、roster 及其代次、玩家身份映射、角色/装备/属性、波次、可恢复菜单/商店状态，以及恢复所需的上游元数据。

主游戏状态和身份附加文件采用同一检查点标识，恢复时只接受匹配的一组，避免“装备来自旧档、身份来自新档”。选择临时文件 + 校验 + 提交标记/安全重命名 + 上一检查点保留的实现，并在目标 Windows 文件系统和 Godot 版本上验证中断行为。

首版采用目标游戏已有安全保存阶段作为检查点，例如支持保存的波次间/商店状态。准确时机在 P0 确认；不默认承诺从战斗中任意一帧恢复。

重连和继续必须验证：相同顺序、倒序、随机顺序加入、部分玩家缺席、原玩家设备改变、不同身份尝试占槽。部分玩家缺席时明确等待或使用受支持的 roster 调整，不自动把缺席角色数据交给新人。

不自动导入两个参考 Mod 的旧存档；如客户有旧档需求，新增可备份、可回滚的迁移器与样本测试。

**10. 分阶段执行与验收**

| 阶段              | 工作与产出                                                   | 完成闸门                                           |
| ----------------- | ------------------------------------------------------------ | -------------------------------------------------- |
| P0 基线与审计     | 安装正版目标游戏及 Mod；恢复调试项目；固定工坊文件哈希；完成 4 人基线；审计两个参考 Mod；整理人数/UI/存档限制清单 | 有可复现基线、版本表、开发环境与问题归因方法       |
| P1 可行性原型     | 按第 5 节验证扩展加载、5 人完整短流程、8 槽位/8 LAN 实例；保留运行证据 | 路线 A 可行或明确失败点；未通过不宣称工坊版兼容    |
| P2 核心与全流程   | 完成容量、虚拟输入、玩家数据、保护脚本、能力协商、战斗与菜单同步 | 5～8 人全流程可用，1～4 人无关键回归               |
| P3 界面与交互     | 交付原风格真实页面样例、确定扩展布局；实现全部页面、焦点、HUD 与显示适配 | 全部槽位可识别、可读、可操作，按基准截图验收       |
| P4 异常与存档     | 落实第 8、9 节机制；注入断线、旧包、重复操作、存档中断；完成恢复流程 | 故障不导致串位、重复经济操作、静默删人或损坏原档   |
| P5 回归与发布准备 | 完成测试矩阵、长时间游戏、性能分析、干净环境安装卸载、版本不匹配验证 | 无阻断性缺陷；兼容报告、已知限制、源码和安装包齐全 |

阶段存在依赖：P0 → P1 → P2；P3 基于 P1 确认的槽位和流程实现；P4 随核心开发逐步加入，最终集中验收；P5 在版本冻结后进行。不能等全部功能完成后才首次测试断线和恢复。

**11. 测试矩阵与明确通过标准**

| 维度     | 验证范围                                                     |
| -------- | ------------------------------------------------------------ |
| 人数     | 1、2、3、4 人回归；5、6、7、8 人功能覆盖；尝试第 9 人应明确拒绝 |
| 联机后端 | LAN、Steam 好友邀请、Steam 公共大厅分别覆盖；必须有跨机器、跨账号 Steam 实测 |
| 输入     | 全键鼠、全手柄、不同机器键鼠/手柄混用、本机手柄拔插和重新选择设备 |
| 流程     | 选人/武器/区域/难度，至少一次全部升级/箱子/商店操作、死亡/复活、下一波、失败与胜利结算 |
| 内容     | 基础游戏及约定 DLC；直接关联多人归属的共享效果、召唤物/炮台、拾取、统计；客户必装 Mod 逐个和组合验证 |
| 故障     | 菜单/商店/战斗/切场景时断线；房主退出；迟到、重复、乱序、旧包；满房；缺扩展和版本冲突 |
| 存档     | 5/8 人保存并以不同加入顺序继续；缺玩家；失效身份；损坏/中断写入；卸载后原版正常使用 |
| UI       | 720p/1080p/1440p、21:9、窗口缩放、长玩家名、中文/英文、长道具描述、极端属性数值与高物品数量 |

自动化优先验证关键状态规则，不为简单常量建立形式化测试。需要有确定随机种子、可重放事件序列的状态测试，覆盖加入/断线/重连/切场景/重复准备/购买/roster 变更；断言身份、人数、队列和经济守恒规则。同步与 UI 结果仍需真实游戏验证。

正式通过标准：

1. 5 人和 8 人各至少完成 3 次完整标准流程，含商店、升级和结算；胜利与失败路径均覆盖。至少一次四人完整回归。
2. 8 人连续游玩累计至少 2 小时，并累计至少 100 次菜单/场景转换，无槽位丢失、卡死、数组越界或重复玩家生成。
3. 对 P5～P8 逐一核对移动、攻击、属性、装备、消费、升级、死亡/复活、统计和存档归属，不能仅凭“画面里有 8 个角色”通过。
4. 在加入、开局、波次切换、存档与恢复完成的提交边界，Host 与 Client 的已提交 roster 和核心菜单状态一致；不比较逐帧表现的完全一致性。
5. 所有第 8 节高风险故障有复现步骤和可验证结果；丢连接和坏档等可接受安全退出，但不能损坏原版永久进度、串位或重复提交操作。
6. 性能门槛在 P0 使用约定硬件、场景和设置定稿。规划目标为常规 8 人场景达到可接受的稳定帧率，记录平均/P95 帧时间、峰值包大小、流量和队列积压；不能仅报告空场景平均 FPS。
7. 网络建议验证正常档位 RTT 50～150ms、抖动约 30ms、丢包 1%，以及压力档位 RTT 300ms、丢包 3%。这些是拟议测试条件；必须区分 RTT/单向延迟，记录工具设置。压力下允许性能下降/超时退出，不允许重复扣款、身份错乱和无限等待。
8. 提交未修复的上游基线问题与新增问题的区分记录；影响约定核心流程的上游问题不能仅通过标注“上游问题”绕过验收，应修复、阻止该组合或变更支持范围。

**12. 兼容发布与升级机制**

- 发布前要求所有成员安装相同且已验证的扩展/适配组合，在进入正式流程前完成验证；不支持混装版本硬开八人局。
- 适配按文件指纹、方法与资源结构判断，manifest 展示版本仅作为辅助信息；未知版本给出原因与支持版本，不直接套用旧补丁。
- 对已知兼容的角色/武器内容 Mod 建立清单，对改写合作槽位、输入、商店、升级 UI 的 Mod 单列适配；没有测试的组合标为未验证。
- 上游更新后重新执行接口差异审查、5 人短流程、8 人槽位/切场景验证和关键存档回归，再更新支持范围。
- 不在用户设备上自动下载或替换 Mod 文件。回滚安装包时同时说明存档 schema 是否可读，保留旧检查点。
- Brotato Online 采用 GPL-3.0；若分发包含其代码的修改/衍生版本，交付相应许可证、修改记录与按许可证要求提供的源码。独立补丁涉及的复用代码同样逐项核对许可。
- 使用游戏运行时已有资源保持原画风，安装包仅包含必要的自有/获许可扩展文件，不打包整个恢复出的游戏工程或游戏资源库。

**13. 交付物、资源与估算方式**

交付物：

- 独立扩展安装包与完整源码、manifest、固定依赖说明；如路线 A 未通过，仅提交验证报告和备选方案，不能把定制分支标为原版兼容包。
- 可重复构建/打包说明、安装/启用/卸载步骤、已知冲突、恢复与故障诊断说明。
- 版本与文件指纹表、每项人数限制的处理记录、API/内部接入点说明。
- UI 基准截图与 5～8 人扩展页面截图，验收录像。
- 测试矩阵、真实 Steam 联机记录、异常注入结果、性能报告、已知限制。
- 超四人存档规范、备份/恢复步骤、升级及回滚说明、许可证和第三方引用清单。

所需资源：目标正版游戏与约定 DLC、匹配的 GodotSteam/Mod Loader 环境、Steam 多账号/设备测试人员、至少能运行 8 个独立客户端的测试资源。LAN 多实例和自动化模拟不能代替最终 8 个真实 Steam 客户端的联机验收。需准备测试专用存档并与日常进度分开。

工期采用“两段估算”：先安排 P0～P1，建议给熟悉 Godot Mod 的开发者约 4～7 个工作日的调研/验证预算，按闸门产出验收；之后依据覆盖数量、独立补丁难度、UI 与故障测试结果重新估算正式开发。该时间是规划预算，不是已验证的完成承诺。初学 Godot、测试设备不足或需要上游新增接口时，不能直接沿用。

正式报价至少区分：核心 5～8 人兼容、原版风格 UI、异常/存档机制、指定 DLC/其他 Mod 适配、后续版本维护。不要把已知的同步和恢复工作当作“后续免费修小 bug”。

**14. 开工前需要锁定的假设**

本计划已能用于技术验证，无需等所有细节确定后才审计源码。但正式承诺交付前，应锁定：最高人数是否为 8、是否强制保持原工坊 Mod 文件不变、目标版本与 DLC、必装其他 Mod、扩展界面布局、存档恢复范围、测试硬件与账号安排。

其中“原工坊版 + 独立补丁”是默认目标。若客户坚持这一点，而 P1 证明当前版本无法可靠扩展，则本项目应给出不可达原因或等待上游接口方案，不能擅自降低兼容要求。
